# 架构评审 — V1 开发日志

> 评审日期：2026-05-08
> 当前状态：开发中，部分模块未完成（api/、facade/、parsers/ 为空）

---

## 总体评价

**合格，结构清晰，有扩展性意识，但有若干值得改进的设计问题。**

---

## 一、优点

### 1. 分层架构合理
`core/`（基础设施）→ `utils/`（工具）→ `processors/`（业务逻辑）→ 空的 `facade/` `api/`（未来入口），层次清晰，依赖方向正确。

### 2. 多态 + 工厂模式
`BaseFileProcessor` 抽象基类定义 `read/process` 接口，具体 Processor 各司其职，`ProcessorFactory` 统一创建，扩展新文件类型只需加一个类 + 改一行 map。

### 3. 安全意识到位
`is_safe_file_path` 做了路径穿越防护和后缀白名单校验。

### 4. 日志设计合格
RotatingFileHandler + 控制台输出，全局单例 logger，工程化基础打好。

### 5. 工具函数职责单一
`file_utils` 管文件 I/O，`text_utils` 管文本清洗，没有职责混杂。

## 二、需要改进的问题

### 问题 1：`parsers/` 与 `processors/` 职责重叠

`processors/` 里的每个子类自己实现了 `read()` 方法（即解析逻辑），导致 `parsers/file_parser.py` 空壳被架空。

**建议**：
- 删掉 `parsers/`，所有解析逻辑留在 Processor 内；或
- 让 Processor 的 `read()` 委托给 `parsers/`（Strategy 模式），真正分离"解析"与"处理"

### 问题 2：`@singleton` 装饰器使用不当

`MdLoaderHolder` 和 `PdfLoaderHolder` 只是保存一个类引用（`UnstructuredMarkdownLoader` / `PyPDFLoader`），本身无状态。Processor 实例本身**不是单例**，但每次都通过 holder 间接持有同一个类引用，多此一举。

**建议**：直接使用类属性存储 loader 类，或彻底去掉 holder。

### 问题 3：`ProcessorFactory` 每次返回新实例

由于 processor 实例无状态，可以缓存复用，但当前每次调用都 `processor_map[ext]()` 新建。

**建议**：改为带缓存的工厂或复用已有实例。

### 问题 4：`clean_text()` 正则过于粗暴

```python
re.sub(r"[^\u4e00-\u9fa5a-zA-Z0-9\s\.,;:!?]", "", text)
```

删除了中文标点（`，。、「」——`）、括号、引号、数学符号等，可能导致知识库场景下的语义信息丢失。

**建议**：放宽正则，根据业务场景保留更多符号。

### 问题 5：缺少入口点和依赖管理

- 没有 `main.py` 或 CLI，项目为"库代码"状态
- 没有 `requirements.txt` / `pyproject.toml`

> 注：此为待完成项，已了解。

### 问题 6：路径穿越检查过于简单

```python
if ".." in file_path:
```

仅做字符串包含检查，不够严谨。

**建议**：使用 `os.path.abspath` 解析后校验前缀是否在白名单目录内。

### 问题 7：类型标注不一致

`save_cleaned_file` 返回类型为 `str | None`（Python 3.10+ 语法），而项目其他地方均使用 `Optional[str]`（3.9 兼容写法），风格不统一。
